# Dispatch Owned Work

Stensibly owns work, context, responsibility, authority, dispatch, and receipts. Glaeda
owns physical execution. Git and GitHub own source and current provider facts. Cultist
may supply selected repository evidence.

## Work from canonical state

- For existing work, read the exact item before acting. Use a compact brief only when
  it changes selection or continuation.
- For new work, create one item with a concrete outcome and bounded project scope.
  Do not create a second queue, coordination record, or status ledger around it.
- Re-fetch current GitHub state with the GitHub plugin when a mutable issue, pull
  request, check, branch, or deployment fact can change the action. Stensibly's
  curated GitHub actions are governed workflows, not a complete GitHub replacement.

## Dispatch exact work

- Select a runner by admitted capability and project authority, not by an informal
  machine preference. Bind the exact source commit and tree when source matters.
- Reuse the existing item, run, claim, and runner-command machinery. Never encode a
  shell command, credential, mutable ref, or workstation path as the durable task.
- Use the narrowest admitted execution profile that can prove the result. A wake or
  liveness signal makes work eligible; it does not grant responsibility or authority.

## Settle from bounded evidence

- Treat the Stensibly receipt as the execution result and GitHub as the source of
  mutable provider facts. Do not copy raw logs, cookies, credentials, or broad machine
  state into chat or work records.
- Exact replay should return the stored result. If an outcome is ambiguous, reconcile
  the owning run before retrying; do not issue a second mutation merely because a chat
  timed out.
- If no eligible runner is available, leave one exact continuation or clearing
  condition on the existing work item. Do not manufacture polling work or a fallback
  queue.
